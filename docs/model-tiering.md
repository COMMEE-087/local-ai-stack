# 模型分层（Tiering）与性能基准

## 思路

不做"一个大模型硬扛所有"，而是**按任务难度/类型分配不同规模的小模型**：

| 层 | 模型 | 用途 | 跑在哪 |
|---|---|---|---|
| **T0 格式化** | 1.5B (Q8) | 命名、极快格式化、简单改写 | 主机 CPU |
| **T1 日常** | 8B | 聊天、拆单、汇总、分发逻辑 | 主机/副机 CPU |
| **T2 执行主力** | 14B | 文档生成、脚本、工具调用 | 副机 GPU |
| **T3 重活/长文** | 30B (MoE) | 复杂推理、长文汇总 | 主机 CPU |
| **视觉** | VL 7B | 看图/OCR/图表识别 | 副机 GPU |

## 为何 14B 放 GPU、30B 放 CPU（看起来反直觉）

- **14B**：模型小，能塞进 12GB 显存，且在 GPU 上达到 **~50 tok/s**（见下），适合**实时交互型生成**。
- **30B**（MoE A3B）：参数量大，塞不进小显存，但 CPU 内存够、且 MoE 激活参数只有 3B，纯 CPU 也能跑到 **~20–25 tok/s**，适合**不要求实时、只要质量**的长文任务。

> 结论：**速度需求 → GPU 14B；质量需求 → CPU 30B**。这是异构硬件下的最优分工。

## 实测性能基准（本架构实际跑出的数字）

> 说明：数值与硬件相关，仅作选型参考。单次测速含冷启动噪声，稳态为准。

### 主机（CPU，8C16T，DDR5）— 三模型常驻

| 模型 | 生成速率 | 说明 |
|---|---|---|
| qwen3:30b (MoE) | **~20–25 tok/s** | 跑热后稳定；8核核显环境 |
| qwen3:8b | ~11–13 tok/s | 日常 |
| qwen2.5:1.5b (Q8) | ~20–23 tok/s | 格式化专用 |

- 三模型**同时常驻 loaded**（主机内存带宽够），切换仅路由转发 0.6–1.7s。
- 30B 首 token 冷启动 ~16.7s，热启动快得多。

### 副机（独立 GPU 12GB）— 一次一个

| 模型 | 生成速率 | 首次冷加载 | 热加载 |
|---|---|---|---|
| instruct-14b | **~49 tok/s** | ~5s | <1s |
| coder-14b | ~49 tok/s | — | — |
| vl-7b (视觉) | ~90+ tok/s | — | — |
| hermes2pro-8b | ~87 tok/s | — | — |
| qwen3:8b (CPU, 副机) | ~12 tok/s | — | — |

- 12GB 显存**塞不下第二个大模型**：切换 = 卸载+加载（14B 约 5–6s，8B/7B 约 2.5–3s）。
- GPU 14B 比 CPU 8B 快约 **3.8 倍**（49 vs 13），印证"实时活走 GPU"。

## 路由规则（经验）

1. **模板化/批量文档** → T1 8B（够用、便宜、快）
2. **实时生成/交互** → T2 14B (GPU)
3. **长文/复杂推理** → T3 30B (CPU) 或云
4. **视觉/OCR/图表** → VL 7B (GPU)，**绝不放 CPU 跑**（慢到不可用）
5. **命名/极简格式化** → T0 1.5B
6. **不确定** → 先试本地，失败回人，不自动上云

## Context Window 预算（小模型的关键约束）

小模型的 ctx 很小（8B≈16–32K，14B≈16–24K），而 **agent 运行时注入的系统提示 + 技能列表 + 工作区文档 ≈ 12K tokens**，会严重挤占。

缓解措施（详见 `skills.md`）：
- 技能**渐进加载**，不常驻注入
- 按 agent **白名单**只注入必要的技能
- 限制 bootstrap 注入的字符数（如 2000/8000）
- 大 ctx 需求走 30B 或云端
