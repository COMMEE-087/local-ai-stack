# 优化经验与踩坑记录

> 这一路跑下来的可复用经验。每条都是实际踩坑换来的，能帮你避免重复劳动。

## 一、系统瘦身（Windows）

用了 Win11Debloat 做系统精简，实测 13 项改动（停 Windows Update 服务、删遥测计划任务、关后台应用等）后：

- **推理速度没有明显退化**（峰值 tok/s 差异属测量噪声）。
- **真正收益在稳定性**：后台任务（更新/遥测）不再随机打断你的推理进程。

> 结论：系统瘦身不是用来"提速"的，是用来**消除后台干扰**的。别指望 tok/s 暴涨。

### 操作铁律
- **先备份注册表**（Debloat 会自动建 `Backups/`，保留备查）。
- 改动前记录基线（性能、状态），改动后可对比。
- 见好就收，别过度精简搞坏系统。

## 二、基准测试的坑

- **请求模板不通用**：不同脚本（如 qspeed/bench）依赖不同的请求模板文件（tspeed.json），缺了就报错。测速前先确认脚本依赖。
- **首测含冷启动噪声**：模型首次加载很慢（30B 首 token 16s+），要**跑热后取稳态均值**，别拿第一次的数下结论。
- **多模型常驻会抢占内存带宽**：主机同时 loaded 多个模型时，单个模型测速会比独占时略低——这是带宽竞争，不是优化失效。

## 三、小模型 Context Window 调优（最关键的坑）

小模型 ctx 有限，而 **agent 运行时注入（系统提示 + 技能列表 + 工作区文档）≈ 12K tokens**，会严重挤占甚至溢出。

### 缓解手段（配套使用）
1. **`tools.profile: "minimal"`**：砍掉大部分工具，只留必需的。⚠️ 但 minimal 极端到**只剩 1 个工具**，必须用 `tools.alsoAllow` 精确补回职责工具（read/write/exec/sessions_* 等），否则 agent 只能回话不能干活。
2. **`skills: []`** + 按 agent 白名单（见 `skills.md`）：禁止技能注入，省 4–5K tokens。
3. **bootstrap 注入限流**：`bootstrapMaxChars` / `bootstrapTotalMaxChars` 限制注入的文档字符数（如 2000/8000）。
4. **大 ctx 任务分级**：需要背大段历史的，改走 30B（大窗口）或云端，别塞进小 ctx agent。

> ⚠️ 实测教训：配了 minimal profile 后**必须**验证工具真的补回来了——"验证通过"可能是假象，实际 agent 只能聊天不能执行任务。

## 四、架构执行的踩坑

1. **常驻 agent 线程不适合多步分发**：ctx 会随任务累积溢出、或"只答不跑"。→ 分发用**一次性 spawn 干净子会话**承接。
2. **子会话继承父模型**：spawn 子件若不显式指定，会继承父 agent 的模型——执行重活必须显式传目标模型（如 14B GPU），别继承 8B CPU 变慢。
3. **汇总 agent 会泛化失真**：让 8B 做"严格逐条合并"时易自己发挥/漏项。→ 加硬约束"严格基于输入逐条合并，不新增不臆断"。
4. **子会话必须清理**：用完带 `cleanup:"delete"` + 超龄自动归档，不留残留，否则常驻会话越多越卡。

## 五、跨平台文件传输（中文文件名）

**Windows → Linux 传中文文件名会乱码**（GBK 进 tar 头，Linux 显示乱码，路径找不到）。

解法：
- 素材先按哈希/ASCII 唯一映射重命名再传。
- 脚本里别用中文字面量判断文件名（会失配），认准 ASCII 别名。
- 复杂逻辑写成脚本文件执行，别在 shell 里堆中文字符。

## 六、PaddleOCR 环境

- PaddleOCR 建议装独立环境（避免污染系统 Python）。若装系统 Python，注意版本（3.13+ 可用）。
- 单页扫描件识别耗时 ~8s（热模型），可作为批量处理的节奏参考。

## 效率哲学

- **一切流程模板化、脚本化、技能化**：做完的事当场沉淀，不重复摸索。
- **先调查现有资产再动手**：避免重复造轮子。
- **测量驱动**：改前后都测，用数据说话，不信感觉。
